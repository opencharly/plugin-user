# 2026.242.2148 — feat(user): groups / not_groups — assert what an account is and is not a member of

## Summary

No charly verb could assert group MEMBERSHIP. `#UserInput` is
`{user, uid, gid, home, shell, linger}` and `#UnixGroupInput` is `{unix_group, gid}` — the
first describes an account, the second describes a group, and neither says whether the
account is *in* the group. So two ordinary assertions had no typed form and had to be shell:

```sh
id -nG user | grep -qx wheel        # the installer put the account in wheel
! id -nG | grep -qw docker          # the desktop user is NOT in docker
```

The second is a security posture, not a nicety: the `docker` group is root-equivalent — a
member can `docker run -v /:/host` its way to passwordless root — so "this image's desktop
user cannot reach the daemon" is a claim a hardened image should be able to make about
itself, in a verb, rather than in a grep somebody can quietly weaken.

Both come from porting upstream Omarchy's acceptance suite, which asserts each of them.

The diff is four files: `schema/user.cue` (the two fields), `params/cue_types_gen.go`
(regenerated), `plugin.go` (the probe), `groups_test.go` (the tests), plus the candy
manifest's own CalVer bump `2026.176.2500` → `2026.242.2255`, which every candy change
carries.

## Why a SET and not a matcher list

Every other list-ish field on a check verb is a `#MatcherList`. This one deliberately is
not, because a matcher runs against the whole subject string:

| matcher | also matches |
|---|---|
| `contains: docker` | `docker-users` |
| `contains: wheel` | `wheel-admins` |

That is not hypothetical. The same trap was found and fixed the same day in the omarchy
beds, where four `mount: {opt: {contains: "subvol=/@"}}` checks each also matched
`subvol=/@home`, `/@log` and `/@pkg` — **all four passed against any one of the four
subvolumes**. For a security posture, a near-miss that reads as a pass is the worst
available failure mode.

Membership is a set question, so the field is a set of exact names: `groups` asserts
presence, `not_groups` asserts absence, both against the parsed field set of `id -nG`,
never a substring of its output.

## Assert-only, like gid

The act form does **not** create memberships. A `user:` install step that silently added an
account to `wheel` or `docker` would be a privilege grant hiding inside an account
declaration; granting a group should be a visible, separate decision.

## One probe, only when asked

Both fields are served by a single `id -nG` call, so a step asserting presence AND absence
costs one round trip. Neither field set means the probe does not run at all — the same
contract `linger` already has, and for the same reason: an unconditional probe would add a
round trip to every existing `user:` step and would fail on a venue where the account has
no resolvable groups.

A failing `id -nG` FAILS the check rather than yielding an empty set. An empty set satisfies
every `not_groups` assertion at once, so the alternative is the check failing open —
silently reporting "not in docker" because it could not ask.

## How tested

Full suite, uncached, complete output:

```
$ go test -count=1 ./...
ok  	github.com/opencharly/plugin-user/candy/plugin-user	0.004s
?   	github.com/opencharly/plugin-user/candy/plugin-user/cmd/serve	[no test files]
?   	github.com/opencharly/plugin-user/candy/plugin-user/params	[no test files]

```

Seven new tests: member passes; non-member fails and the message names the groups the
account actually has; `wheelie` does not satisfy `wheel` and `docker-users` does not trip
`not_groups: [docker]` (the substring trap, asserted in both directions); a real `docker`
membership does fail; both directions in one step; the probe does not run when undeclared;
a failing probe fails rather than passing vacuously.

**Live**, through `charly check box` against a real Arch container, on a charly built with a
local `replace` onto this branch:

```
PASS  check root is in the root group and NOT in docker  [probe-groups]  uid=0 gid=0
PASS  check a bogus group is correctly reported as absent  [probe-groups-negative]  uid=0 gid=0
```

The first exercises `groups:` and `not_groups:` together; the second exercises `not_groups:`
against a name that does not exist at all.

`params/cue_types_gen.go` was regenerated with the real toolchain, not hand-edited:
`cue exp gengotypes` in a temp module headed `@go(params)` / `package params`, then
`spec/internal/schemagen -mode=retag` for the yaml tags — the same two-step `task cue:gen`
runs in `spec`. Diffed against the committed file: the **only** delta is the two new fields,
which is the evidence that the regeneration is faithful.

The test file reuses the repo's existing `multiExec` helper (added for the linger leg)
rather than declaring a second one.
